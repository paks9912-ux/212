# Платформа

Сервер, на котором живёт агент: принимает сообщения из любых каналов, ведёт
диалоги, записывает брони и даёт менеджеру пульт. Зависимостей нет — Node 18+.

```bash
node zaselenie/platform/server.js
```

В логе появятся три адреса: пульт менеджера, демо-сайт с виджетом и точка входа
для каналов.

## Из чего состоит

| Слой | Отвечает за | Файл |
|---|---|---|
| Ядро | один вход для всех каналов, ответы, эскалации | `core.js` |
| Хранилище | диалоги, сообщения, брони, события | `store.js` |
| Сервер | HTTP-API, статика, живые события | `server.js` |
| Каналы | транспорт конкретного мессенджера | `channels/*.js` |
| Пульт | интерфейс менеджера | `panel/` |

Движок, сценарии и база знаний — общие с демо-страницей и автономным ботом
(`../js/`). Платформа их не дублирует, а использует.

## Настройки

Всё через переменные окружения (можно положить в `../bot/.env`):

```bash
PLATFORM_PORT=8080          # порт сервера
MANAGER_TOKEN=длинная-строка # без него пульт открыт всем, кто знает адрес
CHANNEL_TOKEN=другая-строка  # обязателен для каналов, кроме перечисленных в OPEN_CHANNELS
OPEN_CHANNELS=web            # каналы без токена: виджет сайта не может хранить секрет
DATA_DIR=./data              # где лежат диалоги и брони
PULL_SECRET=ещё-одна-строка  # подпись обратного канала виджета
TELEGRAM_BOT_TOKEN=...       # если нужен Telegram
ANTHROPIC_API_KEY=...        # если ответы формулирует модель
```

## Подключение каналов

### Сайт — одна строка

```html
<script src="https://ваш-сервер/widget.js" data-title="Ключи 24"></script>
```

Виджет сам заводит идентификатор диалога, получает подписанный ключ обратного
канала и раз в четыре секунды забирает то, что написали гостю, пока он молчал —
в том числе ответы менеджера.

### Telegram

Задайте `TELEGRAM_BOT_TOKEN` — канал поднимется сам. По умолчанию опрос; для
вебхука добавьте `BOT_MODE=webhook`, `WEBHOOK_URL=https://ваш-сервер/webhook/telegram`
и `WEBHOOK_SECRET`.

### Любой другой источник

Avito, WhatsApp, Instagram, виджет чужой CRM — всё, что умеет слать HTTP:

```bash
curl -X POST https://ваш-сервер/api/message \
  -H 'content-type: application/json' \
  -H 'x-channel-token: ВАШ_CHANNEL_TOKEN' \
  -d '{"channel":"avito","chatId":"12345","text":"есть свободное на выходные?","user":{"name":"Айгерим"}}'
```

Ответ приходит в теле: `{"reply":"...","scenario":"full-request","escalated":false}`.
Чтобы бот сам отправлял сообщения обратно в этот канал, добавьте файл в
`channels/` с методом `send(chatId, text)` — как это сделано для Telegram.

## API

| Метод | Путь | Зачем |
|---|---|---|
| POST | `/api/message` | сообщение гостя из любого канала |
| GET | `/api/pull?chatId=&token=` | что написали гостю (для виджета) |
| POST | `/webhook/telegram` | вебхук Telegram |
| GET | `/api/dialogs?filter=эскалации\|менеджер` | очередь диалогов |
| GET | `/api/dialogs/:id` | диалог с историей |
| POST | `/api/dialogs/:id/takeover` | менеджер забирает диалог, бот молкнет |
| POST | `/api/dialogs/:id/release` | вернуть диалог боту |
| POST | `/api/dialogs/:id/reply` | ответить гостю от имени менеджера |
| GET | `/api/bookings?filter=активные` | брони |
| POST | `/api/bookings/:id/status` | сменить статус брони |
| GET | `/api/holds` | текущие удержания |
| GET | `/api/stats` | сводка для шапки пульта |
| GET | `/api/events` | живые события (SSE) |
| GET | `/api/health` | проверка живости |

Всё, кроме `/api/message`, `/api/pull`, `/api/health` и вебхука, требует
`x-token` с `MANAGER_TOKEN`.

## Пульт менеджера

`http://ваш-сервер/panel?token=...`

- очередь диалогов с фильтрами «нужен человек» и «у меня», метками риска и сценария;
- переписка целиком: видно и что писал гость, и что отвечал бот;
- **взять на себя** — бот замолкает, гость получает ответы менеджера в том же
  канале; **вернуть боту** — агент продолжает с того же места, помня слоты;
- карточка гостя: телефон, язык, что он хочет, бронь с суммами и кнопками смены
  статуса;
- вкладки «Брони» и «Удержания»;
- живые обновления через SSE плюс браузерное уведомление на эскалацию.

## Жизненный цикл брони

```
удержание → ждёт оплату → оплата заявлена → подтверждена
                                           → гость заселился → завершена
                          отменена ← в любой момент      снята ← таймаут удержания
```

Первые три статуса ставит агент, дальше — менеджер в пульте. История переходов
хранится у каждой брони: кто и когда менял.

## Данные

`data/dialogs.json`, `messages.json`, `bookings.json`, `events.json` — атомарная
запись, автосохранение раз в три секунды. В них попадают имена, телефоны и
переписка, поэтому каталог в `.gitignore`, а на сервере держите его с правами
`700`.

Для десятков тысяч броней меняется один файл — `store.js`: интерфейс (`dialog`,
`message`, `booking`, `setStatus`, `bookings`) останется тем же, внутри вместо
JSON будет база.

## Ограничения

- Один процесс: реестр удержаний и контексты диалогов живут в памяти. Для
  нескольких инстансов нужен общий слой (Redis) — это замена двух модулей.
- Платежи не принимаются: агент доводит до «реквизиты отправлены», подтверждает
  оплату человек в пульте.
- Пульт не разделяет менеджеров по ролям: один токен на всех.
